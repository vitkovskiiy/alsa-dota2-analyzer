# Alsa (Dota2 analyzer matches and own stat profile)

Сервіс для командного аналізу в Dota 2. Система фіксує етап драфту, реєструє результати матчів і на їхній основі автоматично перераховує вінрейт конкретних комбінацій героїв ("синергію"). Головна інженерна мета — гарантувати цілісність оновлення масиву статистики під час фіксації результату гри.

## У чому цінність

Звичайні сервіси на кшталт Dotabuff показують лише загальний вінрейт героя. Цей сервіс показує **синергію**: підказує, що герой A і герой B разом мають вінрейт 65%, навіть якщо поодинці кожен із них слабкий — і видає рекомендації під час стадії піків.

Життєвий цикл системи складається з двох режимів:

1. **Накопичення** — після завершення матчу одна транзакція оновлює MMR 10 гравців, глобальну статистику 10 героїв і лічильники синергії всіх пар героїв команди-переможця. Якщо будь-який крок падає — відкат усієї транзакції.
2. **Порад** — під час драфту сервіс за обраним героєм шукає найкращі пари в накопиченій статистиці й повертає топ-рекомендації.

## Стек

- Node.js / fastify
- PostgreSQL 
- REST API

## functional modules

| Модуль | Відповідальність |
| :--- | :--- |
| **Players** | Профілі гравців, поточний MMR, роль (Carry, Mid, Offlane, Support, Hard Support) |
| **Heroes** | Довідник героїв та їхня глобальна статистика (вінрейт, кількість матчів) |
| **Match** | Реєстрація матчу: `id`, статус, переможець, тривалість |
| **Draft** | Зв'язки між матчем, гравцем і героєм — хто ким грав у конкретній грі |
| **Analytics** | Важкі обчислення синергії пар героїв та контр-піків (профільований, винесений в окремий DI-модуль) |

## Модель даних (коротко)

- **Player** — `id`, `name`, `mmr`, `role`
- **Hero** — `id`, `name`, `globalWinrate`, `matchesPlayed`
- **Match** — `id`, `status`, `winnerSide` (`RADIANT` / `DIRE`), `duration`
- **Draft** — `id`, `matchId`, `playerId`, `heroId`, `side`
- **SynergyStat** — `id`, `hero1Id`, `hero2Id`, `matchesPlayed`, `wins`, `winrate`

## Ключові сценарії

### Сценарій 1: Реєстрація результату матчу

**Дія:** сервіс отримує фінальний статус матчу (`isRadiantWin`).

**Оновлення:**
1. Оновлюється статус `Match`.
2. Для 5 гравців команди-переможця: `mmr += 25`; для 5 гравців команди, що програла: `mmr -= 25`.
3. Для героїв команди-переможця: `globalWinrate` перераховується (+1 перемога, +1 матч), для героїв команди, що програла — +1 матч.
4. Команда переможців розбивається на всі пари героїв; для кожної пари в `SynergyStat` інкрементуються `matchesPlayed` і `wins`, перераховується `winrate`.

Якщо будь-який крок падає — весь запис відкочується (rollback), MMR і статистика героїв не розсинхронізовуються.

### Сценарій 2: Запит рекомендацій під час драфту

**Дія:** капітан обрав героя (наприклад, Faceless Void) і запитує кращі пари: `GET /api/draft/recommendations?hero=FacelessVoid`.

**Оновлення:** операція лише на читання. Сервіс шукає в `SynergyStat` усі записи, де `hero1Id` або `hero2Id` — обраний герой, відфільтровує пари з `matchesPlayed > 100` (для відсіювання шуму малих вибірок), сортує за `winrate` і повертає топ-N героїв.

## Інженерні виклики курсу

- **Транзакції:** атомарне оновлення MMR 10 гравців + вінрейту 10 героїв + статистики синергії пар за одну операцію реєстрації матчу.
- **Перформанс:** розрахунок синергії комбінацій героїв на льоту при мільйонах записів матчів — важка операція, яку варто профілювати, винести в окремий модуль (`Analytics`) з DI та розглянути кешування (Redis).

```bash
cd alsa-dota2-analytics
npm install
cp .env.example .env
npm run migrate
npm run dev
```
