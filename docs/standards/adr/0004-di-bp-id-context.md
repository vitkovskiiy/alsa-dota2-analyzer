# ADR 0004: Керування залежностями, business-process ID та контекст запиту

- **Статус:** прийнято
- **Дата:** 2026-10-23

## Контекст

Після уточнень до Завдання 2 необхідно:
- прибрати протягування параметрів контексту через усі виклики методів сервісів/репозиторіїв
- мати business-process ID, який автоматично потрапляє в кожен лог
- винести доступ до БД та транзакції у шар репозиторіїв
- використовувати єдиний глобальний обробник помилок
- керування залежностями без жорсткого зв'язування через імпорти синглтонів скрізь

## Розглянуті варіанти

| Варіант | Переваги | Недоліки |
| ------- | -------- | -------- |
| **Явна передача context у кожен метод** (`service.method(ctx, ...)`) | Простий, явний, легко тестувати | Дужче захаращує підписи, легко забути передати, важко витримати в усіх шарах |
| **AsyncLocalStorage (Node.js)** | Контекст доступний скрізь без передачі параметрів, працює з async/await, підходить для HTTP-запитів | Менш явний, потребує обережності при фоновых завданнях, складніше дебажити |
| **cls-hooked / continuation-local-storage** | Подібний до AsyncLocalStorage, відомий у екосистемі | Додаткова залежність, AsyncLocalStorage вже є в Node.js core |

## Рішення

Використовувати **AsyncLocalStorage** для зберігання контексту запиту (`businessProcessId`, `requestId`). Залежності між шарами зв'язувати через **конструктор** (простіший DI) у `src/container/`. Доступ до БД та транзакції винесено у **репозиторії**.

## Обґрунтування

- `business-process ID` генерується в `onRequest` хуці (або береться з `x-business-process-id`), зберігається в AsyncLocalStorage та автоматично доступний у логах через глобальний error-handler та Fastify-логер
- Сервіси та репозиторії отримують залежності через конструктор, без протягування `requestId/bpId` в кожен виклик
- Репозиторії інкапсулюють `prisma` та `prisma.$transaction`, сервіси містять лише бізнес-логіку, роутинг - лише HTTP

## Наслідки та обмеження

- **Позитивні:** менше boilerplate, уніфіковане логування, чіткий розподіл відповідальностей (routes/services/repositories)
- **Негативні:** контекст неявний, треба стежити щоб `enterWith/run` використовувався коректно
- **Ризики:** при виході за межі async-контексту (деякі воркери) потрібно окремо прокидати контекст. Для HTTP-серверу підходить
