# spec.md — Завдання 2: прототип → інтеграція з БД

## Намір
Реалізувати API для перегляду героїв, матчів та синергії героїв однієї команди для Dota 2 Match Analyzer. Розробка має проходити у два етапи: спочатку всі сценарії читання працюють на статичних даних, потім ті ж самі сценарії інтегруються з PostgreSQL через Prisma. Створення матчу має бути атомарним, ідемпотентним та захищеним від гонок.

## Сутності
- **Hero** (`id`, `name` унікальне, `role`) — довідник героїв
- **Match** (`id`, `externalId` унікальне, `winnerSide` `radiant|dire`, `duration`, `playedAt`) — матч
- **MatchHero** (`matchId`, `heroId`, `side` `radiant|dire`, `won`) — склад матчу, унікальна пара `(matchId, heroId)`
- **HeroPair** (`hero1Id`, `hero2Id`, `totalGames`, `wins`, `winRate`) — агрегована синергія для впорядкованої пари союзних героїв

## Сценарії
| ID | Сценарій | Endpoint | Примітка |
|---|---------|----------|----------|
| S1 | Переглянути список героїв | `GET /heroes` | Статика як fallback |
| S2 | Переглянути героя за ID | `GET /heroes/:id` | `400` невалідний ID, `404` не знайдено |
| S3 | Переглянути матчі з пагінацією | `GET /matches?limit=20&offset=0` | `limit` 1-100, `offset` >=0, сортування за `playedAt` desc |
| S4 | Переглянути матч із героями | `GET /matches/:id` | `400` невалідний ID, `404` не знайдено |
| S5 | Зареєструвати матч і його героїв | `POST /matches` | Транзакційно, ідемпотентно по `externalId` |
| S6 | Отримати найкращі пари героя | `GET /heroes/:id/synergy?limit=5` | Ліміт 1-20, лише союзні герої (`side` однаковий), без N+1 |
| S7 | Стан сервера | `GET /health` | `200 {status:"ok",...}` |
| S8 | Версія сервера | `GET /version` | Містить `sha` з `GIT_SHA` або `dev` |

## Критерії прийняття
- [ ] **Статика спочатку**: `GET /heroes`, `GET /heroes/:id`, `GET /matches`, `GET /matches/:id`, `GET /heroes/:id/synergy` повертають дані зі статичних файлів при порожній/недоступній БД. `POST /matches` вимагає доступної БД.
- [ ] **БД інтеграція**: Використовувати PostgreSQL + Prisma. Схема в `prisma/schema.prisma`, міграції в `prisma/migrations/`. Docker Compose для локального запуску.
- [ ] **Транзакційність**: `POST /matches` створює `Match` та `MatchHero` в одній `prisma.$transaction`. `SynergyService.recompute()` виконує `deleteMany` + `createMany` в одній транзакції.
- [ ] **Ідемпотентність/гонка**: При повторному `externalId` повертати існуючий запис з `created: false`. Обробляти `P2002` при конкурентному вставленні.
- [ ] **Валідація**: Fastify JSON Schema для всіх маршрутів. Додатково: унікальність `heroId`, обов'язкова присутність обох сторін, перевірка існування героїв (`P2003` -> `400`).
- [ ] **Обробка помилок**: Недоступність БД для `POST` -> `503` з `Retry-After: 2`. GET маршрути мають fallback на статику. Невалідний ввід -> `400`. Не знайдено -> `404`.
- [ ] **Синергія без N+1**: Запит пар робити одним `heroPair.findMany` з `OR` по `hero1Id/hero2Id` та `include` героїв. Підрахунок лише для героїв однієї сторони.
- [ ] **Seed**: `src/seed.ts` ідемпотентний (upsert героїв, перевірка по `externalId` для матчів, виклик `recompute()`).
- [ ] **Тести**: Unit-тести з моками БД. Інтеграційні тести з `RUN_DB_INTEGRATION=1` для перевірки на реальній БД.
- [ ] **Документація**: ADR для вибору PostgreSQL та Prisma, `DEFENSE.md` за шаблоном.

## Запити та помилки
- **Читання героїв/матчів/синергії**: при помилці БД/порожньому результаті -> статичні дані
- **POST /matches**: спочатку перевірка `externalId`, потім транзакція; при `P2002` -> повторний пошук та повернення існуючого
- **Синергія**: рахувати пари лише коли `a.side === b.side`, `winRate = wins / totalGames`
